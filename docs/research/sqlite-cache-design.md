# SQLite 本地票据缓存

2026-10-06 用户批准。实现票：[GH-178](https://github.com/vmxmy/orca-factory/issues/178)。依赖 GitHub 账本迁移 PR177；本设计不表示生产已切换。

## 决策

使用 SQLite WAL 持久化票据与评论快照，保留现有 driver JSON 和看板文件接口。GitHub Issues 是唯一远端任务账本；不建立 Linear 同步，不引入 DuckDB。首期目标是减少短命 CLI 与并发调用者的重复读取，并保存可验证的完整性和刷新进度。

SQLite 官方将本地应用存储和远端数据缓存列为适用场景。WAL 支持同机多进程读写并行，但同一时刻只有一个写者；长读事务可能阻碍 checkpoint。数据库存本机磁盘，不放共享网络文件系统。[适用场景](https://www.sqlite.org/whentouse.html) · [WAL](https://www.sqlite.org/wal.html)

## 契约

- 普通发现与展示读取可使用有界 TTL 的完整缓存。强制读取和关键动作复核绕过缓存，远端错误保留为未知。
- 按远端 API、仓库和实际凭据授权范围隔离；不写入明文 token。凭据轮换不得复用旧权限下的缓存。
- 票元数据与评论分别记录新鲜度；父票更新时间不是评论永远不变的证明。
- 网络拉取不占用长写事务。完整批次的数据、版本和刷新完成信息在同一事务提交；分页错误、截断或取消不得发布完整结果。
- 同 scope 的刷新合并；写入前后失效缓存，并用 generation 阻止已开始的旧刷新回填。跨进程协调须有取消与崩溃后的恢复边界。
- 缓存文件和目录限制到当前用户；损坏、权限或 SQL 错误显式返回，不静默重置数据库，不回退 Linear。
- 已发布的 UUID/ZII、GitHub number、owner、correction 预算和执行 checkpoint 不变；快照过期不能授权重新领取或清理资源。

## 接入形状

GitHub → driver 统一适配器 → SQLite WAL → 已发布 JSON → 看板。

SQLite 在技术上允许其他本地进程读取活跃库，但业务调用默认通过 driver，避免看板与表结构绑定。简单用量/失败统计可在现有链路完成；跨大量历史事件的分析出现实测瓶颈后，再单独评估 DuckDB，首期不增加第二套数据库。

选择 `database/sql` 与固定版本 `modernc.org/sqlite`。该第三方驱动不依赖 CGO；版本、底层 SQLite、Go 兼容性及漏洞检查以实际 go.mod、构建和验收输出为准。[驱动文档](https://pkg.go.dev/modernc.org/sqlite)

## 首期存储形状

使用按 scope 隔离的已校验 JSON 投影，记录 generation、更新时间与完整性。首期不是面向外部调用方的关系分析表；调用方通过领域接口访问，避免重复定义当前票据模型。

普通票元数据 TTL 为 30 秒，普通评论 TTL 为 5 分钟。调度器每轮直接读取远端票元数据；执行中或已有归属的票据评论也保持强制读取，以发现父票更新时间不变的新交接记录。默认文件是 `os.UserCacheDir()/orca-factory/github-snapshots/cache-v1.sqlite`，可用 `AGENT_GH_CACHE_PATH` 指定本机路径。Linux 的用户缓存目录通常由 XDG_CACHE_HOME 或 HOME 下的 .cache 决定。

数据库连接在短操作内打开与关闭。刷新用有期限的协调记录合并同 scope 请求，不在网络等待期间持有写事务；缓存不能在 mutation 屏障期间被当作新鲜结果使用。缓存内容按凭据隔离，写入失效按 host/repo 共享，从而使另一授权账号的旧缓存同时失效。刷新操作最多 2 分钟，刷新租约多留 5 秒；写入屏障租约 31 分钟，覆盖现有最多 30 分钟的命令窗口。崩溃后等待租约到期再重新拉取，不把旧行恢复为新鲜结果。

格式版本不支持或非空未标版本的数据库直接报错，禁止自动迁移、清空或删除。实施期间一个旧 CLI 夹具曾写入未发布的默认试验文件 `/home/laoxu/.cache/orca-factory/github-snapshots/cache.sqlite`；已修正测试隔离，原文件保留，正式默认路径采用带版本的新文件。

## 验收与发布边界

先红后绿覆盖重开复用、scope 隔离、失败不提交、TTL、并发刷新合并、mutation 失效、强制读取、取消和文件锁。纯 Go 时钟逻辑可用 synctest，真实文件/WAL 用集成测试。通过根 Make 入口运行 build、vet、lint、test、race、vuln，并验证 CGO_ENABLED=0 构建。

依赖 PR176/177 合并后再验证主线集成和当前 head CI，按 FIFO 合并。发布保留旧二进制和已发布状态；任何数据库删除或数据重置必须有显式要求。缓存可重建不代表有权删除现有文件。

## 本地验证记录

依赖锁定为 modernc.org/sqlite v1.48.2，底层 SQLite 3.51.3，libc v1.70.0；x/sys 单独升级至 v0.44.0，消除扫描器发现的 GO-2026-5024 间接依赖提示。

当前分支的 Make 完整检查通过：831 项普通测试、831 项 race 测试，build/vet/lint/vuln 成功，最终扫描结果为 No vulnerabilities found。CGO_ENABLED=0 构建通过。具体先红后绿日志与固定提交评审证据归档到 GH-178 和关联 PR。

公开接口测试中，3 个独立客户端重复读取同一票及评论，请求数从票元数据 3 次、评论 3 次降至各 1 次。真实子进程测试覆盖并发刷新合并与重新打开复用。该结果只代表夹具中的缓存行为，不代表生产请求量或端到端吞吐倍率。

同样默认 go build 参数下，基线二进制为 14,511,091 字节，引入缓存后约 20.5 MB；不依赖 CGO 的构建约 20.4 MB。新增 SQLite 引擎增加了发布体积。尚未给出生产 RSS、冷启动、磁盘峰值或 p95 延迟基准，不能据此声称性能整体提高。

本地检查不替代最终主线集成、独立评审和远端必需 CI。生产启用仍等待 GitHub 账本完成一次性切换；无部署完成声明。
